### G1 검토 체크리스트

검토하는 사람이 확인할 것입니다. 모두 "예"이거나 고칠 점을 적으면 검토가 끝납니다.

1. 개요의 목적(요금제 추천 자동화)과 요구사항이 맞는가? 빠진 기능이나 필요 없는 기능은 없는가?
2. 남은 `[결정 필요]` 항목에 동의하는가? (보안 결정 3건은 2026-11-07 확정, security.md 13장)
   - 검증 실패 시 다시 쓰기 1회 허용 (requirements.md 5장 8번)
   - 성공 기준의 목표치 (requirements.md 6장)
3. 설계 결정(5장 6~14번)에 동의하는가? 특히 다음 세 가지입니다.
   - RAG는 문장 근거에만 쓴다
   - 숫자는 자리표시자로 쓰고 코드가 채운다
   - 수집·분석은 코드가 먼저 실행한다
4. 아키텍처 그림과 데이터 경계(Claude로 가는 것, Slack으로 가는 것)를 받아들일 수 있는가?
5. 보안 정책(security.md)의 데이터 분류와 통제 목록이 회사의 고객 정보 보호 방침에 맞는가? "고객 안내 요약"(0장)을 고객에게 보여줘도 되는가?
6. 작업 순서와 완료 기준이 납득되는가? 과정 일정 안에 끝낼 수 있는 양인가?

승인하면 아래 "승인 기록"에 날짜와 내용을 적고, 명세·계획·작업 목록의 제목에서 "초안"을 뗍니다.

### STEP 3 구현 — RAG + UI 개발

**순서 원칙(v2.0)**: 셀프 변경과 서류가 시연의 중심이므로 먼저 만듭니다. AI 상담은 답변 규칙과 상담 연결이 확실히 동작하는 수준까지만 만듭니다. "순서" 칸이 실제로 진행할 차례입니다.

이미 끝난 것: 시뮬레이터, MCP 서버(도구 4개), 리포트 숫자 대조와 Slack 메시지 생성. 테스트 31개 통과(11-07 확인).

T4 메모 (11-07)
- 리포트 초안의 숫자는 모두 자리표시자로 쓰고, 검증 뒤 코드가 채웁니다. 아키텍처 검토 때의 실험 4가지(금액 자리 바꿔치기, 지어낸 비율, 한국어 금액 표기, 모델이 계산한 비율)는 모두 "자리표시자 바깥의 숫자"로 거부됩니다. 한글로 쓴 금액("삼십만 원")과 단위 중복("{saving_12m}원")도 막습니다.
- 남는 위험: Claude가 맞는 키를 엉뚱한 문맥에 쓰는 것(예: 추천 설명에 `{current_monthly}`)은 검증으로 잡지 못합니다. 키 이름이 뜻을 드러내고, G3(사람 확인)와 EVAL-04에서 봅니다.
- 두 번째 방어선은 채운 값이 아니라 시뮬레이터 결과 원본과 대조합니다. 채우는 코드에 버그가 있어도 잡힙니다(테스트로 확인).
- "대상 아님 조각"은 조각이 다루는 이벤트가 모두 대상 아님인 조각으로 정했습니다. 응대 가이드처럼 여러 이벤트를 다루는 조각이 하나 때문에 막히지 않게 하기 위해서입니다. 응대 안내 구역에서는 "왜 안 되는지" 설명용으로 인용할 수 있습니다.
- Slack 메시지 제목에서 고객 이름과 `user_xxx`를 빼고 가칭 코드만 씁니다(SEC-12, 전에는 이름이 들어갔음).
- 지식 문서 13개에 `audience`를 붙였습니다(응대 가이드 5개 internal, 나머지 customer). 고객 상담은 `audience="customer"`로 검색해 내부 문서가 나오지 않습니다.

T3b 메모 (11-07)
- 기존 고객 200명의 데이터·고객·가칭 코드·추천 결과가 T3b 전과 같은 것을 지문(해시)으로 고정했습니다(`test_existing_200_customers_are_unchanged`). 성수기 고객 3명은 무작위 값 없이 표로 고정해 맨 뒤에 붙였습니다.
- `user_201`은 3개월 평균만 보면 베이직 유지가 맞지만, 계절 반영으로 계산하면 프로가 12개월 292,000원 쌉니다. 시연에서 "성수기를 보면 추천이 바뀐다"를 보여줄 수 있습니다.
- `user_202`는 장기 고객 할인 대상이라 "유지 + 이벤트"가 됩니다. 성수기 알림은 변경 권유 없는 예산 안내입니다(PRO-08).
- 비교 기간 마지막 달(2027-11)의 기준 달은 2025-11입니다. 2026-11은 아직 기록이 없기 때문입니다. 명세 2장에 적었습니다.
- 해설을 고치다 기존 문제 하나를 찾았습니다: "유지 + 이벤트" 고객(`user_014` 등)에게 "추천 요금제(베이직)로 바꾸면"이라고 쓰고 있었습니다. "이벤트(…)를 신청하면"으로 고쳤습니다. 같은 요금제를 유지하는 성수기 고객에게 "간격이 벌어진다"고 쓰지 않도록, 실제 값으로 간격을 비교한 뒤 문장을 고릅니다.
- 사용량 그래프는 24개월이면 석 달마다 눈금, 점 없이 선만, 성수기 달은 주황 점으로 표시합니다.

T11 메모 (11-07)
- 확인 화면 금액은 서류 모듈과 같은 계산(`documents.build_data`)에서 나옵니다. 검토서, 확인 화면, 변경 확인서의 숫자가 다를 수 없습니다.
- 확인 화면 값의 해시를 접수 때 다시 계산한 값과 대조합니다. 화면을 띄운 뒤 이용 기록이 바뀌었거나 값이 조작되었으면 접수하지 않고 새 값을 보여줍니다(CHG-02).
- 두 번 누르면 같은 접수를 돌려주고, 동시에 눌러도 DB 색인(고객마다 접수 상태 하나)이 두 번째를 막습니다. 다른 내용의 변경은 먼저 취소해야 합니다.
- 적용일은 비교 기간 첫 달 1일(다음 청구 주기), 취소 기한은 그 전날입니다. 기준일이 지난 계산으로는 변경할 수 없습니다.
- 접수 번호에는 일련번호 대신 무작위 6자리를 씁니다(하루 접수 건수가 드러나지 않게).
- 사내 채널 메시지는 만들기만 하고 보내지 않습니다. 실제 전송은 알림 규칙(NTF)과 함께 T5에서 연결합니다.
- 추천 이력 결과값에 "취소"를 추가했습니다(명세 1장).

T10 메모 (11-07)
- 서류 데이터 하나(`build_data`)에서 PDF·DOCX·XLSX·그래프 PNG를 모두 만듭니다. 테스트는 만든 파일을 다시 읽어(XLSX는 openpyxl, DOCX는 python-docx, PDF는 pypdf) 숫자가 시뮬레이터 값과 같은지 확인합니다.
- 세액은 달마다 계산하고 12개월 값은 월별 값의 합입니다. 월별 일정의 합이 시뮬레이터 12개월 총액과 다르면 서류를 만들지 않습니다(`DocumentError`).
- PDF를 눈으로 확인하다가 절감률이 52.5%인 고객(`user_007`)이 52%로 표시되는 것을 찾았습니다. 파이썬 `round()`가 짝수 쪽으로 보내기 때문이어서 0.5를 올리도록 고치고 테스트를 추가했습니다.
- 서류 파일은 저장하지 않고 발행 기록(문서 번호, 해시)만 `app.db`와 감사 기록에 남깁니다. 감사 기록에는 고객 이름과 `user_id`가 들어가지 않습니다(가칭 코드만).
- 한글 글꼴은 `KOREAN_FONT_PATH` → Windows 맑은 고딕 → macOS·리눅스 글꼴 순으로 찾습니다. 작업 공간에는 맑은 고딕이 없어 다른 글꼴로 확인했으므로, PC에서 한 번 열어 보고 확인합니다.
- (사용자 제안) 그래프마다 아래에 해설 문장을 붙였습니다(VIZ-04, `captions.py`). AI 없이 문장 틀에 서류 값을 채우므로 해설 속 금액이 표와 어긋날 수 없고, 해설도 서류 해시에 포함됩니다. 테스트 102개 통과.
- 그래프 색은 dataviz 기준 팔레트(파랑·주황·청록, 순서 고정)를 쓰고 색약 대비 검사를 통과했습니다. 청록은 밝은 배경에서 대비 경고가 있어 같은 값을 표로도 보여줍니다(VIZ-02, 화면은 T13).

T3 메모 (11-07)
